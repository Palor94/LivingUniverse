# Living Universe: instructions for coding agents

Persistent visual character identity is a core architectural requirement, alongside persistent psychology, memory, and world state. Read PROJECT_VISION.md, DECISIONS.md, DEVELOPMENT_PLAN.md, and docs/VISUAL_IDENTITY.md before implementation.

- Preserve each character's stable ID independently of provider, model, name, and timeline.
- Canonical appearance and references normally require explicit user approval. Generated outputs, ratings, ordinary model suggestions, imports, and story events never automatically change canon.
- Owner auto-canon exception (2026-11-06): a scoped machine workflow may write visual canon only under `docs/AUTO_CANON.md` and `DECISIONS.md` (2026-11-06). Whole multi-character frames are never one character’s canon; only character-bound crops with separate face/body evaluation may auto-promote, and uncertain regions must abstain. Numeric gates stay unset until benchmark lock-in. Do not enable live auto-canon writes, model installs, uploads, or paid calls from discussion alone.
- Approval of an output is distinct from promotion to a canonical reference. Canon revisions are immutable, attributed, and reversible through a new revision. Machine auto-canon revisions use a machine actor plus method/model/version.
- Do not invent biographies or appearance details. Unknown values remain unknown. Existing folder names do not prove character identities or approval status.
- Evaluate facial identity and body proportions separately. A face-only similarity score cannot certify character fidelity.
- Keep references, feedback, generation manifests, and training provenance portable. Model-specific adapters and embeddings are derived assets, not the canonical identity.
- Respect Participant versus Creator/Admin knowledge boundaries. Admin data must not automatically enter character prompts.
- Preserve existing media unless the user explicitly chooses the application's Move original action. The user authorized physical organization within this OneDrive resource folder. Moves must verify destination boundaries, refuse overwrites, preserve stable media IDs and character links, and retain a move journal. Never upload or train on the collection without separate authorization. Do not automatically approve the collection outside the gated auto-canon rules in `docs/AUTO_CANON.md`.
- Keep secrets, private character records, media, training weights, and live databases out of Git. Do not publish or configure a remote without authorization.
- Keep live databases, dependencies, caches, and temporary runtime state outside OneDrive. Use deliberate, restorable backups into synchronized storage.
- The user additionally authorized editable original filenames and recoverable catalogue/file deletion. Do not merge, alias, or treat Tibor the admin and Palor the fictional character as one person. Palor is the playable protagonist whom whoever uses the program plays as; the player is not Palor, and Palor is not the admin. Refuse overwrites and path escapes; retain IDs, histories, and a recoverable trash flow. Profile autosave must never approve canon. Cover crops only change presentation. Do not infer that all unnamed background people are one recurring character.
- Build incrementally. No paid generation, training, or continuous simulation by default. Never promise perfect identity preservation or guaranteed reproducibility.

- User retention exception (2026-10-29): removing an approved reference also removes that image from historical reference lists, clears affected reference explanations/proposal copies and invalidates pending approvals. Preserve revision IDs and approved appearance text, other characters, media originals and completed generation manifests. Reference-only changes use minimal reasons; do not invent source-origin claims. Existing offline backups are separate snapshots.

- Owner character policy (2026-10-31, amended 2026-11-10): never create, generate, or accept a female character/profile, including automatically invented supporting characters. Every character is male by default: an unknown or missing gender counts as male and new characters get "Nem: férfi." unless the owner gives another (non-female) value. Estimating gender is allowed (it is no longer forbidden), but it never overrides this default or an owner-set value. Amended 2026-11-14: "hím"/"hímnemű" and any wording describing a being with a penis and testicles (fantasy and non-human beings included) count as male in every rule, and in a gender value these male markers win over female words. Preserve the explicit local character-policy.json enforcement, shared gender guidance, server validation and blocked-identity hashes. Profile/background discussion is not authorization to create additional characters. This overrides any earlier unrestricted character-creation assumptions.

- Complete rename authorization (2026-10-31, amended 2026-11-11): an explicit rename request renames everything: primary name, all text references, canon (appearance, reference notes and earlier canon revisions, rewritten in place), history/provenance text, story events (an approved event stays approved), the ID-owned OneDrive folder, and every file/subfolder name carrying the old name, the shared media library and removed items included. Trusted mode executes it as one backed-up, journaled operation without extra per-part prompts; it is final (no undo; the verified pre-rename database backup is the way back). This is the owner's explicit exception to canon immutability for renames only. IDs, media IDs, file bytes and links are preserved; no overwrites (a taken name is skipped and reported) and no path escapes. Other characters' names containing the old name are never changed. Use synthetic data for tests.

- Explicit crop approval authorization (2026-10-31): the owner designated the authenticated admin crop UI’s Kijelölés mentése action as explicit approval, without a second dialog. It must append an approved reference, preserve all existing references/crops, and commit assignment/draft/canon/audit atomically. Each save and undo creates an attributed revision. This overrides draft-only saves and no-history reference updates for this workflow only; MCP proposal approval safeguards remain.

- Full machine auto-canon authorization (2026-11-06): the owner authorized automatic visual-canon promotion under `docs/AUTO_CANON.md`. Multi-character pictures contribute only per-person crops; abstain on ambiguity; never invent characters. Human crop Save and MCP private Approve remain valid parallel paths. Benchmark numbers and enabling the writer remain separate explicit steps.
- Vision model choice (2026-11-10, replaces the 2026-11-06 gpt-6.1-sol lock): use the model best suited to each job, local or cloud, judged by measured quality, cost, privacy and whether the provider permits the task. Current choices are listed in `docs/VISION_ENGINE.md` (tagging: OpenAI `gpt-6.1-sol` world-v1; character identity: local InsightFace face method, because OpenAI refuses identity matching). Switching a job to another model is recorded in `DECISIONS.md` with its benchmark, and every result keeps its model/method/version in provenance; no silent switch inside a running pipeline. Never reword a request to get around a provider refusal. Paid runs still require an estimate + explicit upload/cost ack; installs, uploads of private media to a new provider and paid calls still need owner approval; no automatic retry of uncertain billed calls; no canon write from tagging alone.
